# Database Schema

## Overview

- **Store:** Firebase Realtime Database (project `dee-and-dee`, `https://dee-and-dee.firebaseio.com`), initialized in `src/firebase.js`.
- **Auth:** Firebase Auth, email/password. The signed-in user's `uid` keys all of their data.
- **Local first:** every write is saved on the device (IndexedDB via localForage, `src/assets/storage.js`). Firebase is only written when a user is signed in. Guest mode never touches Firebase.
- **Access:** all reads/writes go through `src/assets/services.js` (`getCharacters`, `writeCharacterToDb`, `getEncounters`, `createEncounter`, `saveEncounter`, `deleteEncounter`).
- **Security rules:** not checked into this repo. They live in the Firebase console.
- **Not in the database:** the monster search and its saved-monster stack, and spell/weapon/class lookups. Those are either in-memory React state or fetched from the public [D&D 5e API](https://www.dnd5eapi.co). Custom monsters are only stored as part of an encounter.

## Tree

```
/
└── users
    └── {uid}                         Firebase Auth user id
        ├── characters
        │   └── {characterKey}        Push id generated by Firebase
        │       └── Character         (see below)
        └── encounters
            └── {encounterKey}        Push id generated by Firebase
                └── Encounter         (see below)
```

`getCharacters()` reads the whole `users/{uid}` node; `CharacterSelect` then iterates `data.characters`.

## Write flow

Characters are edited locally and synced in one piece:

1. `CharacterSelect` copies the chosen character into the local `character` key (`writeCharacter`, which sets `savedChar: false`).
2. Views edit it through `CharacterContext.updateCharacter`, which rewrites `character` on every change (again `savedChar: false`).
3. `MultiPannelViewer` calls `writeCharacterToDb()` when a panel is saved or switched. It only writes if `savedChar` is false:
   - no `key` yet → a new key is generated (Firebase push id when signed in, `local-…` id in guest mode) and stored on the character
   - the character is written to the local `characters` collection, and to `users/{uid}/characters/{key}` when signed in (full overwrite)
4. After writing it sets `savedChar: true` locally.

There are no partial updates. Each save overwrites the full object.

## Encounters

Managed by `src/components/InitiativeTracker/useInitiative.js`. Conversion to and from app state lives in `encounterData.js`.

### Lifecycle

- **List:** `getEncounters()` reads all of `users/{uid}/encounters` once when the monsters page opens. The page redirects to login if there's no `uid`.
- **Create:** `push` with `turnNumber: 0` and empty lists.
- **Saved (full `set`)** at these points only: starting initiative, every Next/Previous turn, leaving the encounter (back arrow), and ending with **Keep**. Edits between those points (HP, names, rolls, additions) are in memory only.
- **End → Keep:** resets `turnNumber` to 0, `round` to 1, `currentTurnId` to null, and keeps every entry with its HP and initiative.
- **End → Delete:** `remove` on the encounter node.

### Encounter

```js
{
  name: string,
  turnNumber: int,           // 0 = not started (setup). Set to 1 on start, then +1 per Next, -1 per Previous (min 1)
  round: int,                // Shown as "Round N"; increments when Next wraps past the end of the order
  currentTurnId: string,     // id of the entry whose turn it is; absent before start
  monsters: Monster[],
  events: Event[],
  characters: EncounterCharacter[]
}
```

Turn order isn't stored. It's rebuilt by sorting all entries by `initiative` (highest first, missing last), then Dex modifier, then type (character, monster, event), then `id`. The same sort runs when initiative starts, so a reload comes back in the same order.

Firebase drops empty arrays and `null` values, so readers default missing lists to `[]` and a missing `initiative` to "not rolled".

### Monster

```js
{
  id: string,                 // stable per entry, e.g. "goblin-lq3k9x2"
  name: string,               // display name, e.g. "Goblin 2" (editable)
  maxHealth: int,
  currentHealth: int,         // 0 = defeated (greyed out, skipped by Next/Previous)
  initiative: int | null,

  // Handbook monster: the stat block is fetched again from the 5e API on load
  databaseKey: string,        // dnd5eapi index, e.g. "goblin"

  // Custom monster: present instead of databaseKey
  type: string,
  size: string,
  hitPoints: int,             // average HP
  hitDice: string,            // e.g. "4d8+4", may be ""
  armorClass: int,
  speed: string,              // e.g. "30 ft.", may be ""
  strength: int,
  dexterity: int,
  constitution: int,
  intelligence: int,
  wisdom: int,
  charisma: int,
  abilities: MonsterAction[],
  actions: MonsterAction[]
}
```

`MonsterAction`:

```js
{ name: string, description: string }
```

### Event

```js
{
  id: string,
  name: string,
  description: string,
  initiative: int | null
}
```

Just a name in the order. Not linked to the saved `Character` sheets.

## Local storage (IndexedDB via localForage)

`src/assets/storage.js` keeps an in-memory copy of everything, loaded by `initStorage()` before the app renders. Reads are synchronous copies; writes update the copy and save to IndexedDB in the background. On first run, the old `localStorage` keys (`uid`, `character`, `tempCharacter`) are moved over and removed.

| Key | Contents |
|---|---|
| `uid` | Signed-in user's Firebase uid. Present = signed in. |
| `guest` | `true` in guest mode. Cleared on sign-in. |
| `guestBannerDismissed` | `true` once the guest banner is closed. Reset when a new guest session starts. |
| `character` | The character currently being viewed/edited |
| `data/{uid or "guest"}/characters` | `{ [characterKey]: Character }`, local copy of the collection |
| `data/{uid or "guest"}/encounters` | `{ [encounterKey]: Encounter }`, local copy of the collection |
| `tempCharacter` | Legacy. Still read by `BottomNav` to decide whether to show the Spells tab. Nothing in this codebase writes it. |

Collections are namespaced by account, so guest data and each account's data stay separate. On sign-in or sign-up, any guest characters and encounters are added to the account with one multi-path `update` on `users/{uid}`, which leaves existing account data alone. They're then merged into the account's local copy and the guest copy is cleared. If the upload fails, the guest data stays on the device and is tried again on the next sign-in.

**Reads when signed in** come from Firebase. A successful read replaces the local copy of that collection; if Firebase can't be reached, the local copy is used instead. Remote writes don't block the app. Offline, Firebase queues them until it reconnects, but only for the current session.

## Quirks and inconsistencies

- **Two sets of ability score keys.** "New Character" writes `con/dex/str/int/wis/char`. `Skills` reads and writes `const/dex/strength/intelligence/wisdom/charisma`. Only `dex` overlaps, so a new character's scores show as 10 in Skills via the default rather than via the stored values, and both sets end up in the DB.
- **`key` and `savedChar` are persisted** inside the character even though `key` duplicates the node's own path. (`key` is now also what stops repeat saves of a new character from creating duplicates.)
- **`castingLevel` may leak into stored spells.** `Spells` copies the spell array shallowly and sets `castingLevel` on the shared spell objects.
- **Default shapes don't match edit forms.** `addNewWeapon` pushes `dmgType` (the form uses `damType`), and `addCustomSlot` sets `label: 0` instead of a string.
- **Empty-list guards.** `addNewWeapon` and `addCustomSlot` create an empty array instead of adding an item when the list is missing, so the first click does nothing visible. `longRest` falls back to `{}` instead of `[]` for `customFields`.
- **Numbers vs strings.** Many numeric fields come from text inputs and are stored as strings (e.g. `level`, `exp`, `ac`), so readers use `parseInt`.
